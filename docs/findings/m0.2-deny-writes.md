# M0.2 — Deny write tools through the permission path

Question: can a whole provider session be made unable to write, enforced by the harness, with
every denial visible as an event? Invariant 1 depends on the answer.

Reproductions: `docs/findings/repro/m0.2-claude-deny-writes.ts` and
`docs/findings/repro/m0.2-codex-deny-writes.ts`. Run commands are at the top of each file.

## Verdict

| Provider | Enforceable at harness | Mechanism                                                                                             | Denial surfaces as event                                                                             | Verified                                                                  |
| -------- | ---------------------- | ----------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------- |
| Claude   | **Yes**                | `permissionMode: "dontAsk"` + `allowedTools` = read set + `settingSources: []`                        | Yes — SDK `system/permission_denied` → existing `tool.denied` runtime event → `tool.denied` activity | Run here, Claude Code 2.1.270, SDK 0.3.260                                |
| Codex    | **Yes (code-derived)** | thread `sandbox: "read-only"` + `approvalPolicy: "never"`, turn `sandboxPolicy: { type: "readOnly" }` | Partially — as a `failed`/`declined` item, not a dedicated denial event                              | **Unverified**: no `codex` binary or `~/.codex/auth.json` on this machine |

Verdict for the DM view and M1.4: invariant 1 is enforceable for Claude without a prompt-based
substitute. For Codex it is enforceable on paper and must be run before M1.4 relies on it.

## Claude — what the runs showed

Every scenario asked Haiku to write `probe.txt` with Write, then with `echo hi > probe.txt` via
Bash. The file existed after the turn in **none** of them.

| Scenario                                                        | Write                 | Bash                           | SDK `permission_denied` | `result.permission_denials` |
| --------------------------------------------------------------- | --------------------- | ------------------------------ | ----------------------- | --------------------------- |
| `dontask` (recommended)                                         | denied, reason `mode` | denied, reason `mode`          | **yes, both**           | both                        |
| `canusetool` (callback denies, mode `default`)                  | denied by callback    | denied by callback             | **no**                  | both                        |
| `t3-approval-required` (T3's settings sources, callback denies) | denied by callback    | denied by callback             | no                      | both                        |
| `settings-shadow` (project `allow: ["Write"]` loaded)           | denied by callback    | denied by callback             | no                      | both                        |
| `sandboxed-bash` (Bash allowed, OS sandbox denies cwd writes)   | —                     | ran, `operation not permitted` | **no**                  | **empty**                   |

Findings that matter:

1. **Use `dontAsk`, not a denying `canUseTool`.** A callback `deny` blocks the write, but the SDK
   emits no `permission_denied` for it. Denials decided before the callback runs (mode, rule)
   emit one. T3 already maps it:
   `apps/server/src/provider/Layers/ClaudeAdapter.ts:3791` → `tool.denied` →
   `apps/server/src/orchestration/Layers/ProviderRuntimeIngestion.ts:440`. If an adapter denies
   inside `canUseTool`, it has to emit `tool.denied` itself, or the denial is silent. Today's
   approval path emits `request.opened`/`request.resolved`
   (`ClaudeAdapter.ts:4538`, `:4591`). That models a question for the user, not a harness refusal.
2. **Deny-by-default holds in `dontAsk`.** Anything not pre-approved is refused, including tools
   T3 does not recognize. Bare `allowedTools` entries skip `canUseTool` completely: the SDK
   warns `CLAUDE_SDK_CAN_USE_TOOL_SHADOWED`. The allowlist is therefore the whole permission
   model, and should hold only tools that cannot write.
3. **Bash is all-or-nothing at the permission layer.** The callback sees the command string, but
   deciding from a string whether a command writes is guesswork (`find -delete`, git hooks,
   redirections). The OS sandbox (`sandbox.filesystem.denyWrite`, Seatbelt on macOS) does
   enforce it, as the `sandboxed-bash` run shows. The failure surfaces only as an error tool
   result (`item.updated` `failed`), not a denial. v1: no Bash in read-only runs.
4. **Settings sources are a widening risk.** T3 loads `user`/`project`/`local`
   (`ClaudeAdapter.ts:1448`). A project allow rule did not shadow the callback here, most likely
   because of workspace trust in a fresh temp dir; that is not a guarantee in a trusted repo.
   `settingSources: []` removes the question. Note: `settingSources: []` still loads claude.ai
   account connectors (Gmail, Drive, Railway… appeared in `init.tools`). `dontAsk` denies them
   unless allowlisted, but they were not exercised directly.
5. **Two existing T3 paths can widen a read-only run** and must be bypassed for Iskra runs:
   - A user launch arg `--permission-mode` or `--dangerously-skip-permissions` overrides the mode
     T3 sends (`ClaudeAdapter.ts:4695-4699`).
   - `interactionMode` calls `setPermissionMode("plan" | base)` mid-session
     (`ClaudeAdapter.ts:4987-4996`).

## Codex — code-derived, unverified

- T3 already maps `runtimeMode: "approval-required"` to `sandbox: "read-only"` +
  `approvalPolicy: "untrusted"` (`apps/server/src/provider/Layers/CodexSessionRuntime.ts:517-521`,
  turn policy `:566-569`). **This is not categorical.** `untrusted` lets Codex request an
  escalation, and T3 holds it as a user approval (`item/commandExecution/requestApproval`
  `:2052`, `item/fileChange/requestApproval` `:2108`). A human click can then grant the write.
- Read-only for Iskra: `approvalPolicy: "never"`, which leaves no escalation path, or keep
  `untrusted` and resolve every approval request with `decline` right away. Prefer `never`.
- Enforcement is the Codex OS sandbox (Seatbelt on macOS, Landlock/seccomp on Linux). That comes
  from Codex's documented design and was not observed here.
- Surfacing: a blocked shell write comes back as a failed `commandExecution` item, and a rejected
  patch as a `fileChange` item with `status: "declined" | "failed"`
  (`apps/server/src/provider/Layers/CodexAdapter.ts:1013-1020`). There is no `tool.denied`
  equivalent, so the adapter would have to derive one if invariant 1 requires a denial event
  rather than a failed item.
- Gap: MCP servers run outside Codex's sandbox, so an MCP tool with side effects is not blocked by
  `read-only`. Unverified; needs the run.
- Unlike Claude, Codex keeps a **read-only shell**: under `read-only` the agent can still `grep` or
  `git log` while the OS blocks writes.

## Existing T3 modes, per provider

| `runtimeMode`           | Claude                                                                                          | Codex                                                   |
| ----------------------- | ----------------------------------------------------------------------------------------------- | ------------------------------------------------------- |
| `approval-required`     | no `permissionMode` sent (`default`); `canUseTool` asks the user for each non-auto-allowed tool | `read-only` sandbox, `untrusted` approvals              |
| `auto-accept-edits`     | `acceptEdits`                                                                                   | `workspace-write`, `on-request`                         |
| `auto`                  | `auto` (classifier)                                                                             | `workspace-write`, `on-request`, `auto_review` reviewer |
| `full-access` (default) | `bypassPermissions`; `canUseTool` short-circuits to allow (`ClaudeAdapter.ts:4518-4524`)        | `danger-full-access`, `never`                           |

`interactionMode: "plan"` is Claude `setPermissionMode("plan")` and Codex `collaborationMode.mode`.
**None of these modes is a categorical read-only mode.** Iskra needs its own.

## Recommended permission shape (for the spec)

One closed set in `packages/contracts`, resolved per run at run start, deny by default:

```
RunCapabilities = ReadonlyArray<"read" | "write" | "shell" | "network">
conversation run → ["read"]
card run         → ["read", "write", "shell"]
```

Translation per adapter:

| Capability | Claude                                                                                                                          | Codex                                                          |
| ---------- | ------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------- |
| (always)   | `permissionMode: "dontAsk"`, `settingSources: []`, ignore permission launch args, never `setPermissionMode` during an Iskra run | `approvalPolicy: "never"`                                      |
| `read`     | `allowedTools: Read, Glob, Grep`                                                                                                | `sandbox: "read-only"`                                         |
| `write`    | + `Edit, Write, NotebookEdit`                                                                                                   | `sandbox: "workspace-write"`, `writableRoots: [card worktree]` |
| `shell`    | + `Bash` (only with `write`, until sandboxed Bash emits a denial event)                                                         | implicit; the sandbox governs it                               |
| `network`  | + `WebFetch, WebSearch`                                                                                                         | `sandboxPolicy.networkAccess: true`                            |

MCP tools: none by default. Add a per-agent allowlist when a concrete read-only MCP tool is needed.
`tool.denied` stays the single denial event. The Claude adapter gets it for free under `dontAsk`.
The Codex adapter derives it from `declined`/`failed` items.
